## 1. 架构决策：文件即真相（架构 A）—— 已锁定

### 1.1 决策

**磁盘上的 Markdown 文件是唯一事实源。SQLite 是可丢弃的派生缓存。同步走文件级 3-way 合并，向块级演进，不引入 CRDT。**

### 1.2 为什么不是 CRDT（架构 B）

外部建议提出 `Markdown → AST/Block → CRDT → Sync`，其论证例子是"PC 改 Block 002、手机改 Block 004 → 自动合并、两边都保留"。

**这个例子当前代码已经做到了。** `desktop/src/lib/merge.ts` 是完整行级 diff3，`merge.test.ts` 有两条测试逐字对应：

- `:37 两端改不同段落 → 自动合并`
- `:47 两端在末尾各自追加不同内容 → 自动合并（两侧都保留）`

服务端一致性测试 19/19 覆盖 C1 双端顺序 / C2 并发冲突 / C3 删改复活 / C4 幂等 / C5 离线补账 / C7 删除传播。所以对比基线不是"文件覆盖"，而是"已经跑通的 diff3"。

CRDT 相对 diff3 真正多出来的只有三条：

| 增量 | 对本项目的价值 |
|---|---|
| 同一段落并发改 → 确定性合并而非冲突副本 | **未必是好事**：单人多端下字符级交织可能产出 `今天研研究了究了 Agent`，不如两份完整可读的副本 |
| 多人实时协同光标 | 无此需求 |
| 同步载荷更小（只传变更块） | 真价值，但**块级同步 ≠ CRDT**，不上 CRDT 也能拿到（见 §5 P4） |

而代价是一个该方案没有回答的问题：**用户用 Obsidian/VSCode 直接改了磁盘上的 .md 之后，CRDT 状态怎么办？** 只有两个答案，且互斥：

- **块 ID 写进 .md**（如 `^blockid`）→ 外部编辑器会弄丢/弄乱它，且污染文件；"卸载软件后目录里是干净标准 Markdown"这条原则当场破产。
- **块 ID 存旁挂文件**（`.ivyea/crdt/`）→ 外部一改就必须靠文本 diff 重新推导块身份。既然那套 diff 推导无论如何都要写，CRDT 就只在"应用内编辑"这条路上有效，属于为已有能力多养一套机制。

行业佐证：Obsidian Sync 本身不用 CRDT（文件级 + 冲突副本）；Anytype / AppFlowy 用 CRDT，代价是磁盘上没有可直接编辑的 Markdown；Logseq 的 DB 版本为块级一致性放弃了文件即真相，引发社区反弹。**没有产品同时做到"磁盘纯 Markdown 是真相"+"块级 CRDT"** —— 这两条在定义上冲突。

### 1.3 翻转条件（写下来，避免反复讨论）

出现下列任一需求时，才重新评估架构 B，并接受 Markdown 降级为导入/导出格式：

1. 需要"把一篇笔记分享给别人一起编辑"；
2. 需要真正的实时协同光标。

在此之前，任何"要不要上 CRDT"的讨论直接引用本节。

### 1.4 三条不可动摇的原则

1. **数据归用户**：默认存储是用户文件系统里可见的 Markdown 目录；OPFS 只作浏览器版兜底。
2. **索引是缓存不是真相**：SQLite 可随时删除重建；启动按 `mtime+size` 校验，不一致重建单文件；损坏一键全量重建。
   > 这条直接来自 IvyeaAgent 的教训。`ivyea_agent/memory_store.py` 文件头写着："`memory.db` 的历史头号坑就是索引漂移——用户手改 markdown 不进 FTS、重装后 db 丢了而文件还在，于是'文件里明明有、recall 却说没有'。"IvyeaNote 当前犯的正是这个错的加强版（见 §2.1）。
3. **同步 ≠ 上传文件**：冲突必须可见、可选、可回滚，绝不静默覆盖。

## 2. 现状核实（v0.7.4，逐条有代码位置）

### 2.1 P0 缺陷：全库正文索引形同虚设 —— 反链是坏的

`App.tsx:773` 的 `searchDocs`（全库正文缓存）只有一处填充点 `openPalettePreload`（`:784`），且开头是 `if (searchDocs.length > 0) return` —— **建一次，此后永不更新**。触发它的只有 Ctrl+K / Ctrl+O / Ctrl+P（`:804`）、标签面板（`:812`）、图谱（`:1311/:1535`）。

后果：

- **桌面**：没打开过命令面板前，反链面板恒空；打开过之后，新建/编辑的笔记不进索引，搜索结果与反链一起陈旧。
- **移动端**：`MobileView` 的反链区块吃 `backlinks={wikiLinks.back}`（`App.tsx:1408`），而手机上**没有任何入口能触发 preload**（无快捷键，未传标签/图谱入口）。v0.7.3 宣称的「P5 反向链接区块」**在真机上恒不显示**。
- 移动端「🔍 搜索笔记」（`MobileView.tsx:87`）只 filter 文件名，不搜正文。

v1 方案写的"双链跳转/反链准确率 100%（vitest 覆盖解析器）"——解析器确实对，但数据源从未喂进去。**现有 128 个测试全是纯函数单测，抓不住"线没接上"这类缺陷**，这是同类问题反复出现的直接原因。

### 2.2 没有 SQLite / FTS5

`desktop/package.json` 无 `tauri-plugin-sql`。搜索是 `lib/searchIndex.ts`（87 行）的内存 substring 扫描，预载要 `io.read()` 全库文件。1 万笔记 = 1 万次跨 IPC 读盘 + 全量字符串扫描。README 的 M2 行 `[x] 全文搜索（本地索引）` 与事实不符。

### 2.3 没有文件 watcher

全库无 watch/notify 相关代码。外部编辑器（Obsidian/VSCode）改了同一目录，应用不感知；而"可以用 Obsidian 直接打开"是本产品第一卖点。

### 2.4 结构：App.tsx 是 1721 行 God Component

60+ `useState`，同步 / 搜索 / 图片 / 回收站 / 标签页 / 命令面板 / 图谱 / 导入 / 配对 / 更新全在一个组件；两套 UI（`MainView` 395 行、`MobileView` 478 行）靠 props 串。v0.7.4 的"手机像回退了"布局误判、以及 §2.1，都是这个结构的产物：数据流没有边界，漏一根线就静默失效且测不出来。

`index.css` 1817 行同样是按版本累加的分区（`v0.5.0 U3`、`v0.7.2 P3`…），没有设计系统，只有历史。

### 2.5 文档口径不一致

技术方案说移动端 Flutter；优化方案说不采纳 Flutter；`mobile/` 是空目录。README 打勾项与代码不符。

### 2.6 底座是好的，不要推倒

- 服务端 Go：auth/vault/sync/blob/WS/admin/pairing，PG + SQLite 双后端，一致性 19/19，已上线。
- 同步协议 `shared/protocol.md`：cursor 增量、幂等键、版本号冲突检测、墓碑，设计正确。
- 客户端 diff3 合并：正确且有测试。
- 局域网发现（UDP :9999）、扫码配对、应用内更新：都在。

**断裂点全部在桌面/移动客户端的数据层与结构，不在服务端。**

## 3. 目标架构

```
        IvyeaNote 客户端（Tauri 2 + React + TS，桌面 / Android）
                            │
              ┌─────────────┴─────────────┐
              │      Local-first 数据层     │
              │  Markdown 文件 = 唯一真相   │  ← 用户可见、Obsidian 可直接开
              │  SQLite(.ivyea/) = 派生缓存 │  ← FTS5 / tags / links / embeddings
              │  watcher 保证两者不漂移      │
              └─────────────┬─────────────┘
                            │
                   Sync Engine（文件级 3-way
                   → 块级增量，无 CRDT）
              ┌─────────────┼─────────────┐
              ↓             ↓             ↓
         云同步          局域网直连      手动导出
      (Go + SQLite/PG)  (桌面内嵌实例)   (纯 Markdown)
              │
         MCP endpoint ──→ IvyeaAgent（检索 / 写入笔记）
```

## 4. 设计系统（UI 重做）

现状是"每版加一块 CSS"。v2 建立一套可复用的设计层，所有界面从它派生。

### 4.1 定位

**安静的纸。** 笔记软件的界面在用户视线里应该消失，只剩文字。参照对象是 Bear / Things / Apple Notes 的克制，而不是花哨的仪表盘。

### 4.2 三条设计法则

1. **文字是主角**：正文区不放任何常驻装饰；工具条按需浮现（选中文字才出格式气泡，hover 才出文件操作）。
2. **层级靠留白和字重，不靠线和框**：全局最多两级分隔线；卡片/边框能省则省。
3. **动效只用来解释空间关系**：抽屉从边缘推入、面板从触发点展开；不做纯装饰动画。时长 160–240ms，缓动 `cubic-bezier(.32,.72,0,1)`。

### 4.3 Token（替换现有 `:root`）

| 类别 | 规格 |
|---|---|
| 字阶 | 28 / 22 / 17 / 15 / 13 / 11（Large Title → Caption），正文 15px、行高 1.75 |
| 中文字重 | 只用 Regular(400) 与 Medium(500)；**中文标题禁负字距**，大字用轻字重、小字用重字重 |
| 字体栈 | 界面：系统无衬线；正文可切换衬线（思源宋体）；代码：等宽 |
| 间距 | 4 / 8 / 12 / 16 / 24 / 32（8 的倍数为主） |
| 圆角 | 6（控件）/ 10（面板）/ 14（浮层）/ 20（Sheet） |
| 色 | 中性色 12 阶 + 品牌绿单色强调；强调色只用于"当前选中"与"链接"两处 |
| 材质 | 毛玻璃只给真浮层（浮动工具条、命令面板、Sheet），常驻面板一律实色 |
| 阴影 | 两档：浮层 / 拖拽中；其余不给阴影 |
| 深色 | 不是浅色反相：背景 `#16191A` 系，文字 `#E4E9E6`，绿色提亮到 `#7CC95A` 保对比度 |

### 4.4 桌面版式（对标 Obsidian）

│  │  文件树 / 搜索 │  标签页                      │ 大纲 / 反链   │
│R │  / 标签 / 回收站│ ─────────────────────────── │              │
│i │               │  编辑区（可读行宽 720px 居中） │  （可折叠）    │
│b │               │                            │              │
│  │               │                            │              │
└──┴──────────────┴────────────────────────────┴──────────────┘
                     状态栏：路径 · 字数 · 同步状态

- 左 ribbon：文件 / 搜索 / 标签 / 图谱 / 回收站 / 设置（图标 20px，线宽 1.6）
- 侧栏与右栏均可折叠、可拖拽调宽（宽度持久化）
- 编辑区可左右分栏（同文档双视图 / 两文档并排）

### 4.5 高频交互（用户点名项 + Obsidian 对齐缺口）

## 6. 与 IvyeaAgent 的融合

### 6.1 接口是现成的

- `ivyea_agent/retrieval.py` 自述为 *"the stable retrieval boundary for CLI, the local HTTP service, and future IvyeaOps embedding"*，签名 `search(query, *, limit, sources=None)`，`DEFAULT_SOURCES = ("knowledge", "memory")` —— **加一个 `"notes"` source 即接通**，自带词法 + 向量混合检索。
- `ivyea_agent/mcp_server.py` 已是完整 MCP server（tools / resources / prompts），`mcp_client.py` 是 client。

**融合走 MCP，不做代码耦合**：IvyeaNote 暴露 `notes_search / notes_read / notes_write / notes_backlinks`，agent 侧 `ivyea mcp add` 即通，零改 agent 代码；IvyeaOps 也能顺带用上。

### 6.2 分工：Note 是语料库，不是记忆层

**不要把 Note 做成 Agent 的记忆层——Agent 已经有记忆层了。** 两者是不同物种：

| | IvyeaAgent memory | IvyeaNote |
|---|---|---|
| 内容 | "你是谁、你怎么工作"的结构化事实 | 长文语料 |
| 规模 | 几百条 | 几万条 |
| 用法 | 索引层**全量注入** system prompt | 检索取回 |

三层记忆的落法：`Human Notes` = Note 的 .md 文件；`Knowledge Graph` = Note 的 links/tags 表；`AI Memory` = agent 现有 memory + 83 张知识卡。**agent 通过 MCP 只读前两层，不搬家。**

### 6.3 见效最快的一条：Agent 往 Note 里写

现有的 `weekly_review.py`、店铺巡检、飞书 relay 产出直接落到 vault 的 `Agent/YYYY-MM-DD-*.md`，手机上打开 IvyeaNote 即可看。

**"Note 是 Agent 的输出终端"比"Note 是 Agent 的记忆"快十倍见效**：不需要 embedding、不需要语义检索、不需要新协议，就是往同步目录写个 md 文件。而且它立刻给了 Note 一个 Obsidian 给不了的理由。

### 6.4 语义检索：复用，不重写

P3 的语义搜索直接调 agent 的 `retrieval_embeddings`，**不在 TS 里再实现一遍向量检索**。agent 侧已踩过"语义做成重排词法候选是错的"这个坑，没必要踩第二次。

## 7. 品牌与图标

### 7.1 现状问题（三条，均已核实）

1. **不是矢量**：`desktop/src/assets/logo.svg` 是 `<svg><image href="data:image/png;base64,...">` —— PNG 套 SVG 壳，59KB，无法清晰缩放。
2. **元素堆叠**：图标把 y 藤蔓 + 大叶 + 小叶 + 文稿 + 笔共五个物件压进一个画面，60px（手机主屏真实尺寸）下糊成一团绿。品牌主 mark 之所以好看，是因为只有一个主体、留白充足。
3. **透明底**：`icons/icon.png` 带 alpha。iOS 要求不透明；安卓自适应图标会另铺背景层。这是"下载的软件包 logo 不对"的一部分原因。

### 7.2 处理

1. **把品牌 mark 描摹成真矢量**（已完成）：超采样 → 轮廓提取 → 原始密集轮廓平滑 → 多边形简化 → Catmull-Rom 转三次贝塞尔。产物约 3.4KB，可任意着色缩放，作为全项目唯一 logo 源。
2. **子品牌不靠加物件区分，靠底色区分**（Apple 的做法）。Ivyea Note 图标 = 品牌 mark + 设计过的底，mark 占画布约 64%，不透明底。
3. 一份源生成全平台：桌面 ico/icns/png、Android mipmap（前景在内 66% 安全区）、iOS、favicon、应用内 logo。

### 7.3 待定

底色方向 A（纸白）/ B（墨绿）/ C（纸白+折角）三选一，见交付的对照图。

1. **测试三层**（当前只有第一层）：

3. **文档同步**：每阶段完成更新 README「当前进度」，**未实现的不打勾**。
